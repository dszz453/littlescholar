## 先读这段

这个项目**曾经从未被编译过**。原始的开发机上没有 Go 工具链、没有 Docker、
没有 Android SDK。2026-10-12 已在一台 Windows 机器上装入 Go 1.22.12
完成首次真实编译（12,230 行代码，报 4 处错误后全部修好，服务可启动）。

`backend/scripts/lint_offline.py` 的 7 项检查全绿：符号存在性、
接口满足性、实参个数、前后端 API 路径对齐、括号、import、路由对齐。

但请注意：**静态检查全绿不等于能编译** —— 首次真编译就报出了
3 类静态分析查不到的错误（缺导入、指向接口的指针、由此引发的链式报错）。
下面这些是**按概率排序的、几乎一定会遇到的**。
请按顺序处理 —— 前一项不解决，后一项的报错会被淹没。

### 0.1 `go.sum`（已完成，保留供新环境参考）

```bash
cd backend
go mod tidy          # 会生成 go.sum，并给 go.mod 补上 indirect 依赖块
git add go.mod go.sum
git commit -m "chore: 生成 go.sum"
```

> 实测记录：`go.sum` 185 行；`go.mod` 从 17 行 → 75 行，新增 **55 条 indirect**。
>
> **网络提示**：`proxy.golang.org` 在国内网络环境**完全不通**
> （实测 8 秒超时，HTTP 000）。必须先设代理，否则 `go mod tidy` 会报
> 一堆 `Bad Gateway`：
>
> ```bash
> export GOPROXY=https://goproxy.cn,https://goproxy.io,direct
> export GOSUMDB=sum.golang.google.cn
> ```
>
> 实测 `goproxy.cn` 1.16 秒、`goproxy.io` 0.73 秒可用。

**为什么必须做**：`backend/` 下只有 `go.mod`，没有 `go.sum`；
而 `go.mod` 里 `// indirect` 依赖是 **0 条**。11 个直接依赖每个都会拖进
数十个间接依赖，`go mod tidy` 跑完必然生成一大段 indirect 块。
没有，说明从没跑过 tidy。

预期现象：`go.mod` 会**显著变长**（多出 40~80 行 indirect 依赖）。
如果跑完 `go.mod` 几乎没变，说明有问题，别继续。

### 0.2 gradle wrapper（已完成，含一个版本陷阱）

**⚠️ 本轮这里踩了个真坑，务必看完再动手。**

`android/README.md` 原文写「Gradle 8.5 或更高」，但 `app/build.gradle`
用的是 AGP `8.5.2`，而 **AGP 8.5.x 要求 Gradle ≥ 8.7**。
按 8.5 生成 wrapper 后，构建会在 `version-check` 直接失败：

```
> Failed to apply plugin 'com.android.internal.version-check'.
   > Minimum supported Gradle version is 8.7. Current version is 8.5.
```

**结论：wrapper 必须用 Gradle 8.9**（AGP 8.5.x 支持区间 8.7–8.9 的上限）。
仓库里已提交，正常情况下不需要再做这一步。

若日后需要重新生成：

```bash
cd android

# 注意：不能用 `gradle wrapper --gradle-version 8.9`
# 那个形式会去连 services.gradle.org 验证 URL，国内超时后报
# "Test of distribution url ... failed"。
# 必须直接给 --gradle-distribution-url 指向镜像：
gradle wrapper \
  --gradle-distribution-url https://mirrors.aliyun.com/macports/distfiles/gradle/gradle-8.9-bin.zip \
  --distribution-type bin
```

生成后这 4 个文件必须一起提交（**不能被 `.gitignore` 吃掉**）：

```
android/gradlew                             # 纯 LF 行尾
android/gradlew.bat                         # 必须 CRLF 行尾
android/gradle/wrapper/gradle-wrapper.jar   # 二进制，约 43 KB
android/gradle/wrapper/gradle-wrapper.properties
```

> 特别提醒：`.gitignore` 里**千万不要写 `*.jar`** ——
> 那会把 `gradle-wrapper.jar` 一起忽略掉，而这正是"wrapper 缺失"的成因之一。

**验证 wrapper 真的可用**（不需要 Android SDK）：

```bash
cd android && ./gradlew tasks        # 期望 BUILD SUCCESSFUL
```

这会走完整个 Gradle 配置阶段（加载 AGP、解析 settings/plugins），
能验证 `settings.gradle`、`build.gradle`、Kotlin 插件配置全对，
但**不会编译 Kotlin 代码** —— 那需要 Android SDK。

### 预期会遇到的（按概率）

**1) 类型不匹配 —— 概率最高**

12,230 行代码里，跨包传参的类型错误是最常见的。
静态检查只能验证"符号存在"和"实参个数"，**验证不了类型对不对**。

也就是说：报错如果指向某个调的"参数类型不对"，
说明个数是对的、但类型错了 —— 这类问题静态手段查不了。

最该盯的地方：
- `internal/service/transcode.go` —— 转码编排，参数多、跨包多
  （`transcode.Engine` / `task.Accelerator` / `EncryptorLike` 三个依赖）
- `internal/handler/play.go` —— 播放分支多（direct / external / hls /
  transcoding 四种模式），每种的返回结构不同
- `internal/service/resource_alive.go` —— 620 行，双引擎降级，
  `CheckResult` 与 `checkResult` 两套结构容易混

**2) 未使用的变量 / 导入**

已被静态检查覆盖（导入那一项全绿），但**局部变量**未使用查不出来
（脚本不分析作用域）。预期数量不多。

**3) 接口未满足**

已用脚本核验过 6 个实现关系：
- `DiskAdapter` ← quark / baidu / uc / tianyi / aliyun（5 个）
- `EncryptorLike` ← util.Encryptor（1 个）

方法名与返回类型**全部一致**（14 个方法 × 5 个适配器）。
所以这项风险**较低**，但注意脚本没比对**参数类型**——
如果报错指向适配器方法签名，先看参数。

**4) gorm / gin API 签名**

用到的 API 都很常规，且已逐一核对（`Scan` 返 3 值、`Del` 可变参、
`Set` 带 ttl —— 都是 go-redis v9 的正确用法）。

风险点在 `gorm` 的链式调用，特别是：
- `internal/service/permission.go` 的 `Where(strings.Join(conds," OR "), args...)`
  —— **已手工验证三种场景下占位符与参数数量都匹配**，包括有 `path` 为空时
  跳过的情况。这项可以放心。
- `internal/service/transcode_gc.go` 的 `Update("last_access_at", ...)`

### 如果 `go build` 报 `cannot find package`

说明 `go mod tidy` 没跑干净，或者 `GOPROXY` 不通。项目 Dockerfile 里用的是
`https://goproxy.cn,direct`，本地可以先设：

```bash
go env -w GOPROXY=https://goproxy.cn,direct
```

## 第 4 步：`go.sum` 之外，几个已知容易踩的地方

### 4.1 数据库方言

项目支持 PostgreSQL 和 SQLite 两种。代码里已刻意避开
`ORDER BY ... NULLS FIRST`（PostgreSQL 可用但 SQLite 依赖版本），
改用 `last_checked_at IS NULL DESC, last_checked_at ASC`。

**如果用的是 SQLite**：驱动必须是纯 Go 的 `github.com/glebarez/sqlite`
（已如此），不能换成 `gorm.io/driver/sqlite` —— 后者依赖
`mattn/go-sqlite3`，需要 CGO，与 Dockerfile 里的 `CGO_ENABLED=0` 冲突。

### 4.2 ffmpeg 参数

`internal/transcode/engine.go` 用的是：

```
-progress pipe:1        # 进度独占 stdout，错误留 stderr
-profile:v main -level 4.0 -pix_fmt yuv420p
scale=-2:'min(H,ih)'    # 等比缩放，不放大
```

**先在容器里手工验一次最小转码**，再依赖它：

```bash
docker compose exec core-server ffmpeg -version
# 拿一个本地小 mp4 试：
docker compose exec core-server ffmpeg -i /app/data/media/test.mp4 \
  -c:v libx264 -profile:v main -level 4.0 -pix_fmt yuv420p \
  -vf "scale=-2:'min(720,ih)'" -c:a aac -f hls \
  -hls_time 6 -hls_playlist_type vod -progress pipe:1 \
  /app/data/transcode/_probe/index.m3u8
```

注意 `scale=-2:'min(H,ih)'` 里的单引号 —— 在 shell 里有转义问题，
上面用双引号包整个 filter 是正确写法。如果手工跑报错但程序里正常，
说明是 shell 层的问题，不是代码问题。

### 4.3 资源巡检的响应字段

`internal/service/resource_alive.go` 里解析 PanSou / PanCheck 响应的字段名
（尤其 PanCheck 的 `valid` / `status`）是**按公开文档写的，没有抓过真实响应**。

**首次联调时务必抓一次真实响应校准**，否则会出现"巡检跑完但状态全是
unknown"或更糟的"全部误判为失效"。

建议先手动触发范围最小的那一档：

```bash
curl -X POST localhost:8080/api/admin/alive/check \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"mode":"dead"}'
```

`dead` 模式只复查已判死的（数据量最小），确认能正确回写状态后，
再试 `stale`，最后才开定时任务。

## 排错顺序建议（一句话版）

```
preflight 通过（含 AGP ↔ Gradle 版本校验）
  → go mod tidy 出 go.sum          ← 不做这步后面全白搭
  → go build ./...                 ← 类型错误，量最大
  → go vet ./...                   ← 格式串 / 锁
  → docker compose up -d --build
  → curl /api/health               ← 冒烟
  → 手工验一次 ffmpeg
  → 抓一次 PanCheck 真实响应
  → 前端 npm run build
  → cd android && ./gradlew tasks  ← 验证 Gradle 配置（需 JDK 17）
  → cd android && ./gradlew assembleDebug   ← 需 Android SDK
```

## 最后

上面这些判断，全部来自**对源码的静态阅读**，不是运行结果。
如果实际编译报错与本文预测不符，**以编译器的输出为准** ——
我的分析可能有遗漏（这个项目已经有过**四次**"我以为验证过了但实际没有"的
先例，详见 README「离线一致性校验」一节）。

`backend/scripts/lint_offline.py` 全绿只说明"没犯低级错误"，
不代表能编译。真正的判定权在 `go build` 手里。

本文件里 0.2 节那个 AGP/Gradle 版本坑，就是最好的例证 ——
**文件齐了、静态检查全绿、文档也写了"Gradle 8.5 或更高"，
但真跑一次构建，第一秒就失败了**。
静态检查能保证"仓库完整"，只有真构建能保证"能构建"。
